Coat catalog writes accept `name`, `color`, and `size`; update/retirement use `rowVersion`. Item codes are generated internally and remain stable. Apply `CoatColorAndSize` before starting this version. Existing color/size values remain blank until edited. Program snapshots include `nextEligibilityAtUtc` for each employee. Future enrollment delays minute-based eligibility until the enrollment date plus one interval.

Coat variants use `GET/POST /api/inventory/items`, `PUT /api/inventory/items/{id}`, and `DELETE /api/inventory/items/{id}?rowVersion=...`. Writes require `inventory.manage`; updates and retirement require the latest balance version. DELETE retires the variant, preserving allocation and stock history, and requires zero stock. Provision accepts `inventoryItemId` in the same transaction as the stock deduction. Department/season rules no longer have API routes or affect eligibility, import validation, or selection.

Apply `ConfigurableClothingEligibility` before running the API. Clothing settings accept `eligibilityInterval` (1 to 10000) and `eligibilityUnit` (`Minutes`, `Days`, `Months`). Set 1 Minute for testing. A changed policy starts at save time; the first new request is due one interval later. The worker checks every ten seconds. Completed requests remain immutable.

# HR E-Tracker API

Settings are scoped: `GET/PUT /api/settings` owns company, business time zone, and rowVersion; only HR administrators may write. Reads also return a server-derived business date for the header. `GET/PUT /api/clothing/settings` owns module low-stock settings with rowVersion, under clothing read/manage permissions. Clothing Manager alone may write module settings. Eligibility interval and unit are configurable down to one minute for testing. `GET/PUT /api/auth/profile/preferences` saves the current user's personal feed preferences independently of global alert generation. Preferences apply to feed, unread counts, and program snapshots. `POST /api/departments` and `PUT /api/departments/{id}` require HR administrator department-management permission; updates require rowVersion, and active employees prevent department deactivation. Employee and department writes share a transaction guard against concurrent deactivation. Apply `20261004133729_SeparatePersonalNotificationPreferences` before running this version.

HR E-Tracker is a modular HR application. Employees, Inventory, and Workwear share authentication, account administration, departments, and audit infrastructure in one ASP.NET Core API. Inventory is one feature of the application.

The frontend now follows the HR E-Manager demo. `POST /api/program/snapshot` reconciles the current workwear cycle and returns employees with eligibility/status, stock, movements, notifications, and settings for consistent screen updates. Six-month eligibility uses calendar month differences, ignoring the enrollment day; only the current outstanding cycle is generated, and the providing user selects the coat variant taken, independently of department and season. Older outstanding cycles are superseded. Completed allocations remain protected against duplicate issue.

Employee updates accept a unique `employeeNumber`; receipts accept `arrivalDate`. `PUT /api/auth/profile` saves the authenticated user's name/email. Organization settings include `companyName`; clothing settings default to a low-stock threshold of 15. Apply all migrations, including `RestoreDemoProgramSettings` and `SeparatePersonalNotificationPreferences`, before running this version.

Set `ConnectionStrings__DefaultConnection`, `Authentication__Jwt__SigningKey` (at least 32 bytes), `InitialAdmin__Email`, and `InitialAdmin__Password` through environment variables, user secrets, or ignored `backend/.env`. Use `.env.example` as a template. No default login credentials are supplied. The development database is local `SQLEXPRESS`.

From the repository root, apply migrations with `dotnet ef database update --project backend`, then run `dotnet run --project backend --launch-profile http`. The API listens on `http://localhost:5188`; health is `/health`, sign-in is `POST /api/auth/login`, and Swagger is `/swagger` in development. The Vite development server proxies `/api` to that launch profile. Production needs HTTPS and either a same-origin reverse proxy or `VITE_API_BASE_URL` with exact CORS origins.

Identity roles are `HrAdministrator`, `Viewer`, `ClothingManager`, `ClothingViewer`, and the existing `InventoryManager`. HR administration and clothing access are separate: assign an additional clothing role to an administrator who needs that module. Clothing Manager manages employees/imports and clothing workflows; Clothing Viewer reads them. Inventory Manager retains stock/provision access. Viewer has HR read access only. Startup ensures built-in roles exist without automatically assigning clothing roles to users. Explicit feature permissions and server policies live in `Models/AccessPolicies.cs`; auth and user responses include effective permissions. The frontend hides unavailable features and actions, while the API enforces every permission. New modules require explicit grants. Users & access manages built-in role assignments; custom role definitions are deferred. Account edits invalidate sessions, and the last active administrator is protected. Clothing notifications are filtered out for HR-only accounts.

Access tokens last 15 minutes by default; refresh tokens rotate and have an absolute seven-day session lifetime. The frontend keeps access tokens in memory and restores sessions on reload using a persistent HttpOnly refresh cookie. Refresh tokens are never returned in response JSON. The cookie is scoped to /api/auth with SameSite=Strict and Secure enabled outside local HTTP development. Login, refresh, and logout require X-HR-Auth: 1 (also set this header in Swagger). Refresh has no request body. Logout can revoke the cookie session without a bearer token. Separate frontend/API origins must be on the same site, use HTTPS in production, and be explicitly listed in Cors:AllowedOrigins; credentialed CORS is enabled. Prefer a same-origin reverse proxy. Database records persist independently of browser sessions. Configure the initial administrator before first startup. Successful bootstrap records local state in ignored `identity-bootstrap.json`; remove that file after resetting the database or deleting bootstrap accounts/roles.

Run `dotnet test backend/HrETracker.slnx --configuration Release`. Set `HR_ETRACKER_SQL_TESTS=1` to also run integration tests against isolated local SQLEXPRESS databases. Frontend verification is `npm run typecheck`, `npm test`, and `npm run build` from the repository root. See `BUILDPLAN.md` for the delivery status and remaining acceptance checks.
